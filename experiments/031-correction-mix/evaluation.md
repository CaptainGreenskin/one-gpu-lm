# 031 开发执行与回放

本页补充已在训练前冻结的三组对照。科学规则以 `cycle-spec.json` 的 `development.variants`、预算、顺序和 `analysis` 字段为准：**base / original025 / mixed031**。顶层 `implementation_gate` 的“四臂”字样继承自025，未用于031调度；三组及540次运行在训练前已明确，保持原文件哈希便于审计。

开发集是自025以来已观察的60道题，不宣称新的独立题；6个来源家族与训练来源及其关联家族隔离，最终测试不读取。每个权重、每题3次：540个新工作区。按预先冻结的十题分块顺序执行，实际计划52次模型加载，上限54次。每次加载与所有失败成本都记录，不挑有利轮次，不自动重跑。

三者复用同一 `evaluation_rollout`、同一原生工具历史、同一关闭思考的模型配置，以及024的反馈规范化。每题限制12次调用、每次512生成token、总6144生成token、8192输入token和600秒代理时间。独立判分在代理预算外计时，不向代理反馈隐藏检查；超预算的正确补丁仍不记为预算内成功。

权重身份有三层检查：启动前核对适配器所有文件；每次加载记录后端实际暴露的权重身份；每条轨迹绑定该组的完整有效协议并核对后端身份。原025→新031虽然都属于学生，仍强制停进程并重新加载。模拟集覆盖这个易漏的切换，不能只按“底座／学生”二分复用后端。

训练完成后，CPU审计使用真实tokenizer重建完整选择，逐条对齐1,006条记录、输入与监督token、126次更新和最后6条累积。还检查原父数据、采集审计、保存重载探针、参数检查与全部冻结文件。只有完整候选通过，才能冻结准确适配器哈希和开发实现，通过公开字节验证与完整CI后开始新开发评分。

运行结束后，CPU审计逐条回放请求、生成token ID、模板编码、工具反馈变换和已有判分记录，核对每次调用预算、模型身份、所有成本与52次计划加载的顺序。它不调用模型、不重新执行测试命令、不另起一轮挑分。中断轨迹、未知在途生成和缺失配对保留并阻止通过门槛。

可复用模块与入口：

- `python -m one_gpu_lm.verified.mixed_training_audit --root <工作区> --protocol <候选协议> --out <核验回执>`：CPU训练完整性核验。
- `python -m one_gpu_lm.verified.mixed_eval_watch --root <工作区> --protocol <开发协议>`：唯一有时限的开发执行。已有运行路径时拒绝覆盖。
- `python -m one_gpu_lm.verified.mixed_eval_audit --root <工作区> --protocol <开发协议> --out <审计回执>`：全部原始请求回放。
- `python -m one_gpu_lm.verified.mixed_report --training <训练结果目录>` 或 `--results <开发结果目录>`：由公开数字复算表格、门槛和曲线；`--no-figures` 只需标准库。

公开统计、代码、固定规则和数据身份；私有任务、轨迹、原始代码和模型权重不随报告上传。换自己的文档或仓库应建立自己的任务准入、来源许可与独立留出，不可把本轮结果直接套用到自己的场景。
