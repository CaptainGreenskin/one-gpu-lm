# 028：从实际错误补丁状态接手

027 的纠错流程修好 26/32 道训练题，但只有 1 条合格多次纠错示范；25 道成功题只修改了一次。028 先验证能否从已有训练轨迹恢复足够多的真实错误补丁现场，再决定是否启动模型采集。最终测试继续封存。

## 第一阶段：历史状态准入

只扫描 025 正式训练采集、026 训练接手、027 训练纠错这三轮已审计的 310 条轨迹；不读取开发或最终测试轨迹作为样本。初步只读盘点有 24 个“源码已修改且命令返回运行错误”的候选状态，涉及 11 道题、4 个来源家族。这个计数不是合格状态数：复合命令失败不证明补丁仍然错误。

执行前固定 [admission-protocol.json](admission-protocol.json)：

1. 每条历史轨迹按调用顺序扫描，保留每种源码状态第一次实际运行错误；排除原始故障、未执行请求、超时、输出限额错误、缺失源码及未审计记录。
2. 在新的离线沙箱里重放该调用之前的真实操作，逐步核对源码哈希、保护文件、退出状态与规范化后实际反馈。工具历史不重写，不取用后续修复或参考答案。
3. 对重建状态**重新单独执行声明的可见回归**。只有真实运行错误且源码和保护文件未改变，才确认该状态仍未修好。此检查属于新增 CPU 验证，会单独记账，不冒充原模型执行过的命令。
4. 依次按 025、026、027 的登记顺序选择每道题第一个确认状态，再按固定哈希、来源家族轮转，最多 12 道不同任务。选择不用历史轨迹未来是否成功作条件。
5. 至少确认 **6 道不同任务、3 个来源家族**，才允许准备后续 GPU 采集。若不足，发布所有准入和拒收结果，不增加题目、放宽复核条件或启动训练。

CPU 准入最多 30 分钟、1024 次实际工具执行，每条命令最多 60 秒；初步盘点的 24 个候选全部保留去向，无自动重试。新增模型调用、参数更新均为 0，隐藏判分不参与状态准入。

恢复出来的是“经过内容与反馈核对的历史前缀，再加一次当前可见回归确认”。它不等于保存了历史 inode、时钟和进程内存。未来两组会从同一份新快照开始，文件内容、权限、mtime 与完整可见历史相同。

## 条件性的后续阶段

准入通过后，再公开冻结具体状态列表、快照哈希、提示规则、两组预算和训练数据门槛，才启动唯一一次配对采集。计划比较同一 27B 底座的原流程与纠错流程；两组得到相同的接手预算，历史调用成本与新增成本分别记录。历史失败动作只可作为上下文，最终经过验证的成功修正才可作为正向训练目标。

采集通过也不代表模型已提升：之后还需冻结单候选训练和开发验收方案。最终测试、原始源码、工具轨迹和权重保持私有。当前 CPU 准入不授权自动发布参数。

## 实现与测试

`one_gpu_lm.verified.failure_states` 提供候选扫描、受限重放、可见回归确认和快照准入。8 项 CPU 单元测试覆盖真实失败链、复合命令假阳性、反馈变化、测试文件篡改、未来答案泄漏、原始故障/超时排除、确定性去重与执行预算。
