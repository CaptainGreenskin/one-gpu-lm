# 023 · 工具反馈与重复评测稳定性

本轮不训练，也不选发布模型。固定底座、020 recovery 和 022 action，在同一批 15 道开发题上对比原始工具输出与规范化元数据后的输出，各重复 3 轮，共 270 次任务运行。最终测试继续封存，023 目录只接收开发任务，不复制最终题。

两种条件使用同一原生工具协议、进度提示、greedy 解码和预算：每题最多 12 次调用，单次最多 8192 输入 / 512 输出 token，总输出最多 6144 token，任务最多 900 秒。模型按拉丁轮换顺序加载，每个模型/轮次内逐题交错两种输出条件，每题从新的缺陷源码副本开始。完整执行顺序在 protocol.json 中冻结。

`metadata_v1` 只改输出文本中的两类完整行：标准 `ls -l` 元数据行的月/日/时间，及 JavaScript 测试汇总行的耗时。保留权限、所有者、大小、文件名、测试数量和成败。先沿用原始 2400 字符截断，再做规范化并再次限制长度，不能因规范化读到原本截断掉的源码。命令、文件、错误信息、退出码和独立判分输出不改。任意源码/日志日期、地址、PID 及未匹配字段不处理；这不是所有波动源的解决方案。完整行模式可能无法辨别恰好长得相同的用户文本，适用范围限于本批代码任务，原始与交付输出均私有留档供审计。

每次模型加载还对两道已诊断开发题的固定初始请求各生成两次，共 36 次独立探针调用，单次上限仍为 512 token。不执行这些探针返回的命令，不计入或替代任务分数。记录实际 CUDA/框架设置，不调整确定性开关。相同输入产生不同输出，与相同动作收到不同工具反馈，分别统计。

主要指标是各模型/条件的三轮通过数、分数范围、跨轮有通过/失败翻转的任务数，以及 45 个任务-轮次对中的成败不一致比例。另报告首次编辑、未编辑失败、逐调用输入/输出/反馈哈希、135 组同轮原始/规范化配对、成本和硬件采样。第一次轨迹分叉用于定位观察到的差异，不把后续所有失败归因为单一字段；本轮组合干预也不能分别识别日期和测试耗时的独立贡献。

全模型流程上限 16 小时，包含加载、探针、270 次任务及加载后的控制。已完成任务不补跑；可恢复故障仅在原路径、原截止内从完整步骤恢复，保留失败记录。不完整配对不计入配对率，明确披露分母。样本仅 15 道重复使用的开发题、4 个仓库、3 轮，不能作为通用编码能力或模型发布证据。

运行顺序：CPU clean/broken/restored 控制 → 权重、来源及固定探针输入核验 → 公开冻结与 CI/匿名内容核验 → 唯一控制器 → 实际请求/反馈/源码和环境审计 → 汇总曲线及公开数值。精确原任务和轨迹保留私有；公开代码允许在新协议下使用自己的授权开发任务，不能替换本次冻结输入。
