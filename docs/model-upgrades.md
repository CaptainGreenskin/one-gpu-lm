# 底座升级时，哪些成果应该留下

本项目的长期资产是可以反复检验模型的流程和证据。未来千问或其他模型出现新版本，不能只替换模型名、重新画一条 loss 曲线；应该能回答：原来的哪些任务变好了、哪些退化了、同等预算下是否值得迁移。

当前仓库编码链路的实现按 [one_gpu_lm 模块职责](../one_gpu_lm/README.md)划分。更换基模优先调整 `models/` 与独立 profile；数据、训练、评测和服务通过明确接口复用。新的架构仍需验收，旧 LoRA 不假定可以直接迁移。

## 成果放在哪里

| 资产 | 主位置 | 复用方式 |
| --- | --- | --- |
| 数据处理与来源台账 | GitHub 代码、格式、哈希；原始素材受控存储 | 沿用来源/授权/署名记录、去重规则、仓库级拆分，重新分词即可；新 tokenizer 的长度预算必须复测 |
| 任务与判分系统 | GitHub harness；训练/开发/秘密测试内容分别管理 | 相同任务、工具、判分和预算比较新旧模型；反复查看过的测试转为回归集 |
| 训练流程 | GitHub 通用代码 + 独立模型 profile | 复用冻结主干、LoRA、记录、保存重载；新架构重新验收目标层与内核 |
| 性能基准 | GitHub 协议与原始测量 | 在同一硬件/精度/输入输出长度/并发下，比较显存、卡时、TTFT、解码速度与失败率 |
| 可用的具体模型版本 | ModelScope 模型卡与合规发布包 | 固定底座提交、适配器哈希、使用方式、限制和关联 GitHub 结果；未验收不标记推荐 |
| 运行经验与失败原因 | GitHub 实验报告；infra-guide 解释原理 | 记录触发条件、修复、复验和适用范围，避免升级时重复踩坑 |

截至 011，已实现前三项的函数级小规模版本及自动产物。参见 [通用组件的实际范围](../training_lab/README.md)。

012 已把这些契约用于固定开源仓库上的构造修复任务；[repo_lab](../repo_lab/) 提供本地 agent 后端、独立副本评分及完成工具步骤后的进程恢复。[36 道完整对照](../experiments/012-repository-agent/results/2026-11-09/)中，开发与独立留出逐题结果均未改善，旧回归保持 9/9，候选未达到晋升门槛。构造任务与真实历史 issue 的结论要分开；新底座的生产部署基准仍未完成。

## 新基模接入协议

1. **登记身份。** 官方仓库、精确提交、权重/配置/tokenizer/许可证哈希、允许的使用与分发范围。镜像下载也要核对相同字节。保留旧模型与环境。
2. **接通模型适配。** 在独立 profile 中声明加载类、chat template、特殊 token、dtype、LoRA 目标层。检查 missing/mismatched keys；执行有限长度生成、反传、保存重载。架构改变时检查 attention、KV/recurrent state、position encoding 和所需内核，不假定旧适配器兼容。
3. **先测未训练版本。** 沿用冻结的任务/工具版本和预算；按语言、任务类别、难度报告成功率、回归、超时和编译失败。不要先训练，再回忆底座成绩。
4. **一次只改一个主要因素。** 先保持同一合法训练集和训练方法；如比较相同卡时与相同训练样本量，应分开成两种实验。不同 tokenizer 下 token 数不能直接当作相同训练量。
5. **按预定规则选择。** 开发集用于早停与选择，最终留出不参与训练、蒸馏轨迹生成或反复调参。用任务级配对和多个训练种子核对改善，不能仅看平均 loss 或一个幸运样例。
6. **验收实际使用。** 多文件改动、隐藏测试、原有测试回归、工具预算、长任务中断恢复和上下文压缩分别计量。扩大上下文窗口不是通过长任务验收。
7. **发布并保留回滚。** 公开 GitHub 的协议/指标/失败分析；合规且通过质量门槛的模型再发布 ModelScope。模型版本明确链接到代码版本、数据身份、运行报告和推理命令；原版本继续可识别。

新的任务集建立时先固定指标、通过门槛与不允许退化的类别。当前没有足够的仓库任务来设定可信的数值阈值，因此不把 9 道 smoke 题的分数伪装成正式上线标准。

## 每次运行的最小产物

`profile.json`、`source.json`、`environment.json`、`data.json`、下载/加载回执、训练记录、前后配对结果、硬件采样、失败记录，以及自动生成的实验报告/数据卡/模型卡。每种结构带 schema 版本，公开文件按清单列出哈希。保存 raw 数据/权重和公开运行证据是两个不同操作。

我们衡量沉淀是否有用，看下一次接入能否少改代码、减少排错、沿用同一把评测尺子，以及另一位贡献者能否拿自己的合法任务跑出同格式结果。文件数量和下载了多少模型不作为项目进展指标。


014 在基础设施验收之后增加[固定候选质量筛查](../experiments/014-coding-quality/)：训练覆盖审计、全新仓库留出、历史能力回归、实际 adapter 身份检查以及先冻结后评分的晋级门槛。更换基模时可以复用这些合同和工具，但已经看过结果的任务应转成历史回归；新的独立留出任务与新基模的兼容性仍需重新验收。
