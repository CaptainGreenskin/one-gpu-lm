# 工具对话接入契约

模型能生成一段 shell 命令，并不代表它在下一轮能正确识别命令的执行结果。接入新底座时，应分别检查工具定义、动作解析和历史消息序列化。[016](../experiments/016-tool-roundtrip/)隔离比较最后一项；其任务全部是历史回归，不能作为独立效果证明。

## 当前实现的边界

[`render_history`](../one_gpu_lm/common/tool_history.py)是一个无副作用的序列化函数。它不执行命令、不修改原始审计记录，也不修补模型生成的不完整动作。当前只支持**每轮一个 `bash` 工具、一个 `command` 参数、紧接着一个执行结果**。多工具并行、工具调用 ID 对齐和其他模型家族的模板需要单独实现与验收。

| 输入消息 | `native_schema` | `native_roundtrip` |
| --- | --- | --- |
| 系统与用户任务 | 保留角色和正文 | 相同 |
| 已接受并实际执行的 assistant 动作 | 保留原始正文 | 保留动作外的文字；动作转为 `tool_calls` |
| 紧随其后的实际执行结果 | `role=user` | `role=tool`，正文不变 |
| 格式错误反馈 | `role=user` | 相同，不冒充执行结果 |

转换必须同时满足：结果带执行器的 `extra.tool` 元数据；上一条消息是 assistant；严格解析器重新接受该动作；解析值与记录的 `extra.actions` 完全相同；正文中恰好找到一个支持的动作片段。转换后的文字会去掉首尾空白。任一条件不满足就报错，不能猜测应执行的命令。

这条信任边界位于执行器内部：外部用户输入不能自行声明 `extra.tool` 或 `extra.actions`。更换工具系统时，需要继续由可信执行器写入这些字段。

## 新底座接入顺序

1. 固定权重、tokenizer、chat template 和依赖版本，保存内容哈希。先核验模型许可证与来源。
2. 用本地合成历史验证角色、参数和结果内容；覆盖正常调用、错误反馈、空结果、带特殊字符的命令以及元数据不匹配。已有用例在 [`tests/test_tool_history.py`](../tests/test_tool_history.py)。
3. 用**实际固定 tokenizer**回放可授权的历史前缀。未启用新策略时，token 数组必须与旧实现完全一致；启用时，检查模板是否真正接收调用结构与工具结果，而非仅检查 Python 字典。
4. 保留原始历史，同时记录每次请求的工具调用/结果数量、输入 token、生成 token、格式解析结果和上下文处理结果。最终从原始轨迹核对这些回执，不能只信计数器自身。
5. 在同一任务、判分、模型和预算下，单独比较序列化策略。公开冻结协议后再跑模型，保留全部结果和逐题退步。已经观察过的任务用于诊断；采用新策略还需新的独立任务。

016 的预检回放了 1,000 个历史前缀，保留了旧策略编码一致性及调用/结果配对证据。它检验的是这个模型版本与这份模板，未来版本仍需重跑。

## 失败时如何定位

| 现象 | 先核对的证据 |
| --- | --- |
| 模型写出了工具调用，执行器却拒绝 | 完整输出是否触及生成上限、工具名/参数名、严格解析器的判定 |
| 一直重复读取同一文件 | 原始动作与结果是否正确配对、模板中的结果角色、请求预算；重复本身不证明序列化有错 |
| 上下文超限 | 裁剪前后 token 数和实际输入上限；单独试验上下文策略，避免与格式变更混在一起 |
| 格式合规但测试仍失败 | 修改文件与独立判分结果；工具格式正确不等于修复正确 |

对外可发布契约、代码、哈希、聚合指标和失败分类。原始命令、文档、仓库快照、任务答案和轨迹按各自授权处理。当前公开报告不含这些输入，因此复用流程与逐字重现当前分数是两种不同能力。

原始实现采用 MIT 许可，模型及上游素材的权利单独核验。通用消息结构参考 [Transformers 工具对话文档](https://huggingface.co/docs/transformers/chat_extras)；具体编码以经过验证的固定模板为准。
